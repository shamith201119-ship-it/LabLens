Never invent fake progress.

Do not show 65% completion because three seconds passed.

→ `uploading`
→ `upload_complete`
→ `extracting`
→ `structuring`
→ `ready_for_review`

Map extraction state to actual extraction job status.

Map structuring state to the actual structure operation.

Only move to ready-for-review when the data is actually available.

- Keep the user informed.
- Poll using the existing job API.
- Show that processing is still happening.

- Do not restart completed operations unnecessarily.

Handle:
- Upload errors.
- Extraction errors.
- OCR failure.
- API timeout.
- Structuring errors.
- Invalid report.
- User navigation away and back where appropriate.

The user must not be trapped in an endless animation.

The application should explain:

## 10.1 Separate facts and possibilities

Clearly distinguish:

FACT:
"The result is above the reference interval printed by this laboratory."

POSSIBLE CONTEXT:
"Several factors can influence this measurement."

NOT ESTABLISHED:
"This result alone cannot determine the cause."

## 10.2 Symptoms and personal context

The user wants to understand which symptoms may be relevant.

This must be handled carefully.

Only show symptom/context information supported by the relevant medical source.

Use wording like:

"Your doctor may want to know whether you've experienced any of the following..."

Do not assume the user has these symptoms.

Do not generate a diagnosis based on symptom selection.

If adding a personal context form:
- Make every field optional.
- Explain why the information may be useful.
- Keep it local to the report/consultation workflow where possible.
- Do not store it in unrelated backend tables.
- Never send it to external search providers.
- Do not infer symptoms automatically from laboratory values.

## 10.3 Safe next steps

The product should provide useful actions without pretending to be a doctor.

Appropriate guidance includes:
- Confirm the original value.

- Discuss out-of-range findings with a healthcare professional where appropriate.
